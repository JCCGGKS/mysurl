# 短链系统 V8 数据规模增长优化方案

## 1. 目标

随着短链数量、用户数量和跳转流量持续增长，系统的主要问题会从“功能是否完整”逐步转向“核心链路是否还能稳定支撑更大规模”。

本方案的目标是：

- 梳理当前实现已经具备的扩展能力
- 识别未来数据规模继续增长时的主要瓶颈
- 给出贴合当前项目结构的分阶段优化路线
- 明确哪些优化应该优先做，哪些应该延后

本方案聚焦当前仓库已有实现，不讨论过度超前的复杂架构。

## 2. 当前实现基础

结合当前代码，系统已经具备以下可扩展基础：

- 跳转链路优先查 Redis `short_code -> original_url` 缓存
- 不存在短码通过 Bloom Filter 预过滤
- 跳转缓存 miss 时使用 `singleflight` 合并回源
- 创建链路支持按用户 + 规范化长链复用已有短链
- 批量创建支持请求内去重、批量查库、批量写库、批量回填缓存
- `visit_count` 采用 Redis 增量聚合，后台异步批量回刷 MySQL

这些能力说明当前项目已经完成了从“直接查库”到“缓存 + 异步聚合”的第一阶段优化。

## 3. 当前主要访问路径

### 3.1 跳转链路

当前跳转链路大致为：

1. 校验 `short_code`
2. 查 Redis 精确缓存
3. 缓存 miss 时查 Bloom
4. 进入 `singleflight`
5. 回源 MySQL
6. 回填缓存
7. Redis `INCR` 访问增量

特点：

- 读多写少
- 热点明显
- 对响应延迟最敏感
- 最容易因为缓存失效而产生瞬时回源压力

### 3.2 创建链路

当前创建链路大致为：

1. 校验并规范化长链
2. 查 `long -> short` 缓存
3. 查 MySQL 是否已存在
4. 不存在时生成短码
5. 写 MySQL
6. 回填缓存和 Bloom

特点：

- 流量通常低于跳转链路
- 更依赖唯一约束和查重索引
- 容易受到发号策略和唯一冲突影响

### 3.3 列表与后台查询链路

当前用户列表链路会执行：

- 一次 `count`
- 一次游标分页查询

特点：

- 在数据量小时简单直接
- 在数据量变大后，筛选、分页、总数统计会逐步成为后台接口瓶颈

## 4. 数据量增长后的主要瓶颈

当数据规模从十万、百万继续增长到千万以上时，主要瓶颈通常不在 Go 语法层，而在数据存储和访问模型。

### 4.1 MySQL 单表持续膨胀

当前核心表是 `short_links`，承载了：

- 短码映射
- 用户归属
- 访问次数
- 创建时间
- 状态与软删除

问题：

- 单表越来越大后，索引维护成本上升
- 列表、筛选、统计类查询会变慢
- `visit_count` 更新会让热点行持续被修改

### 4.2 Redis 缓存键持续增长

当前缓存包含：

- `short_code -> original_url`
- `user_id + original_url -> short_code`
- `shortlink:visit:{id}` 增量 key
- Bloom Filter

问题：

- 当前映射缓存是永久 TTL，数据越多，占用内存越大
- 冷数据长期驻留 Redis，性价比变差
- visit 增量 key 数量变大后，扫描和回刷成本上升

### 4.3 统计字段和主表耦合

当前 `visit_count` 仍然回写到 `short_links` 主表。

问题：

- 主表既承载静态映射，又承载高频统计字段
- 访问热点会持续更新主表中的同一行
- 后续如果要做更多统计维度，主表会越来越重

### 4.4 后台查询成本上升

当前列表接口返回总数，并支持筛选。

问题：

- `count(*)` 在大表上成本会越来越高
- 用户筛选条件增多时，复合索引设计会更复杂
- 后台读流量可能和核心跳转链路争抢数据库资源

### 4.5 热点短链带来的瞬时压力

虽然当前已经有 Redis 缓存和 `singleflight`，但在极端热点场景下仍有风险：

- 缓存失效后会有短时间集中回源
- 单实例 `singleflight` 只能抑制本机重复请求
- 多实例下热点保护仍然有限

## 5. 优化原则

在当前项目阶段，建议坚持以下原则：

- 优先优化读链路，因为跳转流量通常远大于创建流量
- 优先减少 MySQL 主表压力，而不是优先增加业务 goroutine
- 优先减少 Redis 无效驻留数据，而不是盲目堆缓存
- 优先把统计数据和主业务映射逐步解耦
- 优先做低改动、高收益优化，再考虑分库分表和复杂异步系统

## 6. 分阶段优化路线

### 6.1 第一阶段：中小规模优化

适用场景：

- 数据量进入十万到百万级
- 已经能明显感觉到列表查询、缓存规模、访问统计开始变重

建议优先做的事情：

### 6.1.1 优化 `short_links` 索引设计

当前表已有：

- `uk_short_code`
- `uk_user_original_url`
- `idx_user_id`
- `idx_url_hash`

建议根据真实查询路径补充索引，而不是只保留单列索引。

优先考虑：

- `(user_id, deleted_at, id)`，用于用户列表游标分页
- 根据后台筛选是否常用，再评估 `(user_id, deleted_at, short_code)` 或其他复合索引

原则：

- 索引要服务真实查询 SQL
- 不要为了“以后可能会用”而堆过多索引

### 6.1.2 为 Redis 映射缓存设置 TTL

当前 `short -> long` 和 `long -> short` 缓存使用永久过期。

建议：

- 为映射缓存设置合理 TTL
- 热点数据允许不断续期
- 冷数据自动淘汰

收益：

- 避免 Redis 内存随着业务历史数据线性膨胀
- 提高缓存空间的有效利用率

### 6.1.3 让缓存值更轻量

当前 `short -> long` 缓存值使用 JSON。

建议：

- 如果后续压测确认序列化成本明显，可改成更轻量的结构
- 例如拆字段、使用更短的编码格式，或只缓存必要字段

收益：

- 降低 Redis 存储体积
- 降低序列化和反序列化成本

### 6.1.4 持续强化批量能力

当前批量创建已经具备较好的批量访问能力。

建议继续保持：

- 批量查缓存
- 批量查库
- 批量写库
- pipeline 回填缓存
- 批量发号

原则：

- 能批量就不要拆成多次网络往返
- 当前批量上限不高，不建议优先改成多协程并发小操作

### 6.2 第二阶段：主表减压

适用场景：

- `short_links` 表明显成为核心压力点
- `visit_count` 更新和后台查询开始影响跳转主链路

建议优先做的事情：

### 6.2.1 拆分访问统计

建议逐步把 `visit_count` 从主表思维中拆出来。

可选方向：

- 单独维护 `short_link_stats` 统计表
- 主表只保留短码映射和核心元数据
- 统计表异步聚合更新

收益：

- 减轻主表更新压力
- 让跳转映射和统计数据职责分离
- 为后续增加更多统计维度预留空间

### 6.2.2 弱化强一致 total

当前列表接口每次都查总数。

建议：

- 评估后台页面是否真的必须实时返回精确 total
- 若不是强需求，可改成：
  - 仅返回当前页数据和 `has_more`
  - total 走延迟统计
  - 或只在筛选变化时计算一次

收益：

- 降低大表上的统计查询压力

### 6.2.3 后台查询与主链路隔离

建议在流量继续增长后逐步引入：

- 读写分离
- 报表或后台查询走只读库
- 跳转主链路优先依赖主库 + 缓存

收益：

- 避免后台读请求影响跳转核心路径

### 6.3 第三阶段：高流量与高热点优化

适用场景：

- 跳转流量明显高于后台管理流量
- 出现少数超热点短链
- 多实例部署成为常态

建议优先做的事情：

### 6.3.1 增加本地热点缓存

当前跳转链路主要依赖 Redis。

建议：

- 在实例内增加小型本地热点缓存
- 形成“本地缓存 + Redis + MySQL”三级读取路径

收益：

- 减少 Redis RTT
- 在热点短链场景下进一步降低外部依赖压力

注意：

- 本地缓存只适合做小规模热点保护
- 不适合作为全量缓存

### 6.3.2 强化热点失效保护

当前已有 `singleflight`，但它是单实例粒度。

后续可按需要考虑：

- 热点 key 逻辑永不过期
- 后台异步刷新
- 多实例场景下增加更强的热点保护机制

原则：

- 不要为了所有 key 引入复杂机制
- 只针对少数热点 key 做重点保护

### 6.3.3 改造访问统计聚合模型

当前访问统计采用：

- Redis `INCR`
- worker 定时 `SCAN`
- 批量回写 MySQL

当 key 数量进一步增大后，可考虑：

- 使用消息队列或 Redis Stream 聚合访问事件
- 消费端批量写入统计表
- 降低对 keyspace 全扫描的依赖

收益：

- 更适合高流量持续写入场景
- 回刷链路更容易水平扩展

### 6.4 第四阶段：超大规模存储演进

适用场景：

- 数据量进入千万到亿级
- 单表、单库、单 Redis 实例已不再适合长期承载

建议优先做的事情：

### 6.4.1 为 `short_links` 提前设计分片方案

核心问题是先确定分片键。

若核心流量主要是按 `short_code` 跳转：

- 更自然的做法是按 `short_code` 或其 hash 路由

若后台管理大量按 `user_id` 查询：

- 需要评估是否保留用户维度辅助索引表
- 或增加面向后台查询的冗余模型

原则：

- 分片键必须服务主查询路径
- 不要只从“数据平均分布”角度选分片键

### 6.4.2 主数据与查询模型分离

当主数据规模过大时，通常不应继续依赖“一张表服务所有场景”。

可考虑：

- 跳转主链路使用面向 `short_code` 的主存储
- 后台管理使用单独的查询模型、索引表或离线汇总表

收益：

- 不同场景不再争用同一套存储结构

## 7. 结合当前项目，最值得优先落地的事项

如果基于当前仓库现状排优先级，建议顺序如下：

1. 优化 `short_links` 相关复合索引，优先服务用户列表和筛选查询
2. 给 Redis 映射缓存增加 TTL，避免冷数据长期驻留
3. 评估并逐步拆分 `visit_count`，降低主表写压力
4. 弱化列表接口对实时精确 total 的依赖
5. 为未来分片明确方向，先完成表结构与查询模型上的准备

这几项比“继续增加 goroutine”更重要，也更符合当前项目的真实瓶颈。

## 8. 不建议当前阶段优先投入的方向

以下事情不是不能做，而是不应该在当前阶段抢优先级：

- 为普通批量请求引入大量多协程并发
- 过早引入复杂分布式锁
- 在没有真实热点问题前引入过重的本地缓存体系
- 在数据量还不大时直接做分库分表改造
- 为统计字段追求过强一致而大幅增加系统复杂度

原因是：

- 当前系统的主要收益仍来自减少存储压力和网络往返
- 过早复杂化会抬高维护成本

## 9. 结论

随着数据量不断增大，短链项目的优化重点会从“接口功能补齐”转向“读链路稳定性、主表减压、缓存可控增长、统计解耦和存储演进”。

对当前项目来说，下一阶段最关键的判断不是“代码还能不能跑”，而是：

- `short_links` 主表是否越来越重
- Redis 缓存是否无限增长
- `visit_count` 是否继续拖累主链路
- 后台查询是否开始与跳转流量争抢资源

只要优先把这几类问题拆开处理，系统就可以在现有结构上继续平稳演进。

## 10. 可优化方向总结

结合当前实现和后续规模增长趋势，可继续优化的方向可以归纳为以下几类：

- 存储层优化：围绕 `short_links` 的真实查询路径补齐复合索引，提前降低大表分页、筛选、统计查询成本，并为后续分片预留结构基础
- 缓存层优化：为 `short -> long`、`long -> short` 映射缓存设置 TTL，压缩缓存 value 体积，控制冷数据长期占用 Redis 内存的问题
- 统计链路优化：逐步将 `visit_count` 从主表中解耦，转向独立统计表或独立聚合链路，减少热点更新对核心映射表的影响
- 查询链路优化：弱化后台列表对实时精确 `total` 的依赖，并在后续通过读写分离或只读库隔离后台查询压力
- 热点保护优化：在极端热点场景下增加本地热点缓存、热点 key 续期和更强的失效保护，避免缓存抖动时集中回源
- 批量处理优化：继续坚持批量查缓存、批量查库、批量写库和 pipeline 回填，优先减少网络往返而不是盲目增加并发
- 架构演进优化：当数据量进入更高量级后，再逐步推进按主访问路径设计的分片方案，以及主数据模型与后台查询模型分离

如果用于实际排期，建议优先级仍然按照“先减主表压力、再控缓存增长、再拆统计链路、最后做大规模架构演进”的顺序推进，这样收益更直接，改造风险也更可控。
